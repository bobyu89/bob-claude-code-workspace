# PRD：AI Statistical Platform（`aistat`）第一階段 MVP

來源：`docs/2026-10-20_產品與工程設計需求書_v1.md`（需求書 v0.1）。本 PRD 把需求書第 7 節 MVP 與第 14 節驗收標準落成可實作規格，並對第 16 節「待決設計事項」採用預設決策（見「實作決策」標註 **[預設]** 者，可日後推翻）。

## 問題陳述（Problem Statement）

護理與醫療研究者、研究生多半不是統計或程式專家。現行工具（SPSS 等）只把數字丟給使用者，不說明為什麼選這個方法、資料是否符合前提、結果能推論到哪裡；而直接請 LLM「幫我跑統計」又會出現捏造數值、無法重現、病人資料外流的風險。使用者需要一個能被 AI Agent 操作、但所有數值都由真實統計引擎算出、每一步都有審查與紀錄、並且能教會使用者的分析流程。

## 解決方案（Solution）

提供開源 CLI `aistat` 與共用的 Core 服務：

1. 使用者在本機建立 workspace，匯入 CSV / Excel；系統保存唯讀原始檔與雜湊，產生資料字典與品質報告。
2. 使用者（或 AI Agent 代為）建立分析計畫：指定方法與變項角色。系統執行 **JEV Gate A**，以 YES / NO / UNCERTAIN 逐項說明方法是否適用；NO 擋下，UNCERTAIN 需使用者明確確認。
3. 只有使用者核准後，系統才產生分析程式碼（R 或 Python），以子行程交給真實統計引擎執行，保存程式碼與原始輸出。
4. 系統從原始輸出生成 APA 7 結果草稿（繁中或英文），並以 **JEV Gate B** 檢查草稿中每個數字都能追溯到原始輸出、p 值格式正確、沒有因果過度推論。Learning Mode 另外產生以使用者自己資料為例的教學說明。
5. 每次分析是一個獨立的 run 資料夾，可匯出成果包、可重新執行並核對輸出。
6. MCP Server 與 Agent Skills 讓 Claude Code 等 Agent 透過同一個 Core 服務操作，CLI 不連 LLM 也能完整使用。

## 使用者故事（User Stories）

### Workspace 與資料匯入

1. 身為研究生，我想用 `aistat init` 在專案資料夾建立 workspace，以便把資料與分析結果集中管理。
2. 身為研究生，我想 `aistat import` 一份 CSV，以便開始分析。
3. 身為護理研究者，我想 `aistat import` 一份 Excel（.xlsx）並可指定工作表，以便直接使用醫院匯出的檔案。
4. 身為研究者，我希望匯入後原始檔被保存為唯讀副本，以便確保研究資料不會被意外修改。
5. 身為研究者，我希望每份資料集都有 SHA-256 雜湊，以便日後證明分析用的是哪一版資料。
6. 身為研究者，我希望重複匯入同一份檔案時系統能辨識（同雜湊），以便不產生重複資料集。
7. 身為研究者，我想 `aistat datasets` 列出已匯入資料集，以便選擇要分析的那一份。
8. 身為研究者，我希望匯入失敗（檔案不存在、格式不支援、空檔、欄名重複）時看到清楚的錯誤訊息，以便自行修正。

### 資料檢查與資料字典

9. 身為統計初學者，我想 `aistat inspect` 看到資料預覽（前幾列），以便確認匯入正確。
10. 身為統計初學者，我想看到每個變項的型態、測量尺度（nominal / ordinal / scale）、缺失數與相異值數，以便理解自己的資料。
11. 身為研究者，我希望系統標出可疑問題（缺失比例高、常數欄、重複列、疑似 ID 欄、數值欄但只有少數幾個值），以便在分析前處理。
12. 身為研究者，我希望品質檢查結果寫成 `quality_report.md`，以便放進研究紀錄。
13. 身為研究者，我想用 `aistat dictionary set <變項> --level nominal` 修正系統推論錯的測量尺度，以便後續審查使用正確尺度。
14. 身為研究者，我希望資料字典記錄尺度是「系統推論」還是「使用者確認」，以便審查時知道可信度。
15. 身為研究者，我想把資料字典匯出為 `data_dictionary.csv`，以便附在論文附錄。

### 分析計畫與 JEV Gate A

16. 身為研究生，我想用 `aistat plan --method paired-t-test --var before=pre --var after=post` 建立分析計畫，以便明確定義要做的分析。
17. 身為研究者，我希望系統檢查方法與變項尺度是否相容（例如 t 檢定的結果變項必須是 scale），以便不會做錯分析。
18. 身為研究者，我希望獨立樣本 t 檢定的分組變項若不是恰好兩組時被擋下，以便改用合適方法。
19. 身為研究者，我希望配對 t 檢定時系統要求我確認前後測是同一批受試者，以便不會把獨立樣本誤當配對。
20. 身為研究者，我希望系統說明缺失資料的處理方式（listwise / 完整配對）與影響人數，以便評估是否合理。
21. 身為研究者，我希望系統列出這個方法需要檢查哪些統計假設，以便知道執行時會檢查什麼。
22. 身為研究者，我希望樣本數不足以執行分析時被擋下並說明原因，以便知道要補資料或換方法。
23. 身為研究者，我希望 Gate A 的每項判斷以 YES / NO / UNCERTAIN、證據、理由、需要的動作保存到 `method_review.json`，以便事後追溯。
24. 身為研究者，我希望計畫有任何 NO 時無法核准，以便系統真的守住關卡。
25. 身為研究者，我想用 `aistat approve <RUN> --confirm pairing_structure` 確認 UNCERTAIN 項目並核准計畫，以便進入執行。
26. 身為研究者，我希望我的確認動作與時間被記錄，以便日後證明是人工確認過的。
27. 身為研究者，我希望未核准的計畫無法執行，以便遵守「分析計畫未經核准不得執行」。

### 執行

28. 身為研究者，我想 `aistat analyze <RUN> --engine r` 用 R 執行分析，以便使用學界最常見的開源統計引擎。
29. 身為研究者，我想 `aistat analyze <RUN> --engine python` 用 SciPy / statsmodels 執行，以便在沒有 R 的電腦也能分析。
30. 身為研究者，我希望不指定引擎時系統自動選擇可用引擎（R 優先），並把選擇結果記錄下來，以便不用煩惱設定。
31. 身為研究者，我希望系統把實際執行的 `analysis.R` / `analysis.py` 存進 run 資料夾，以便自己或審查者重跑。
32. 身為研究者，我希望引擎原始輸出存成 `raw_outputs/results.json` 並記錄引擎名稱與版本，以便追溯每個數值。
33. 身為研究者，我希望指定的引擎沒有安裝時看到清楚訊息（例如找不到 `Rscript`），並且 run 不會被標成已執行，以便知道要安裝什麼。
34. 身為研究者，我希望引擎執行錯誤或逾時時 run 變成 FAILED 並保存錯誤訊息，以便不會產生假的結果。
35. 身為研究者，我希望系統只執行白名單內的引擎指令並設有逾時，以便執行環境安全。
36. 身為研究者，我希望引擎同時執行該方法的假設檢查（常態性、變異數同質性、期望次數等），以便在報告中說明前提是否成立。

### 統計方法

37. 身為研究者，我想做描述性統計（n、缺失、平均、標準差、中位數、四分位數、最小最大值；類別變項的次數與百分比），以便描述樣本。
38. 身為研究者，我想做配對樣本 t 檢定，並得到平均差、95% CI、t、df、p、Cohen's d_z 與差值的 Shapiro-Wilk 常態檢定，以便評估前後測改變。
39. 身為研究者，我想做獨立樣本 t 檢定，得到 Welch 與 Student 兩種結果、Levene（Brown-Forsythe）檢定、各組描述統計、Cohen's d，以便比較兩組。
40. 身為研究者，我想做卡方獨立性檢定，得到 χ²、df、p、Cramér's V、交叉表與期望次數檢查，以便分析兩個類別變項的關聯。
41. 身為研究者，我想做 Pearson 或 Spearman 相關，得到係數、p 值與（Pearson 的）95% CI，以便描述兩變項的關聯。
42. 身為研究者，我想做基本線性迴歸，得到各係數 B、SE、t、p、95% CI、標準化 β，以及 R²、調整後 R²、F 檢定、殘差常態性與 VIF，以便建立預測模型。

### JEV Gate B 與報告

43. 身為研究者，我想 `aistat review <RUN>` 對報告草稿執行 Gate B，以便在輸出前檢查。
44. 身為研究者，我希望 Gate B 確認結果確實來自引擎原始輸出，且資料雜湊與匯入時一致，以便確認沒有被竄改。
45. 身為研究者，我希望 Gate B 檢查草稿中每個數字都能對應到原始輸出或計畫參數，以便攔下 LLM 捏造或打錯的數字。
46. 身為研究者，我希望 Gate B 檢查 p 值符合 APA 7（不寫 p = .000、小於 .001 寫 p < .001、不加前導零），以便符合期刊格式。
47. 身為研究者，我希望 Gate B 檢查效果量與信賴區間存在且合理，以便報告完整。
48. 身為研究者，我希望 Gate B 偵測因果過度推論用語（例如「證明」「導致」），以便在非實驗設計中避免錯誤結論。
49. 身為研究者，我希望 Gate B 檢查「達顯著／未達顯著」敘述與 p 值、α 一致，以便文字與數字相符。
50. 身為研究者，我希望 Gate B 把假設檢查違反的情況標為 UNCERTAIN 並建議替代方法，以便我做出判斷。
51. 身為研究者，我想 `aistat review <RUN> --draft my_edit.md` 審查我（或 AI）改寫過的草稿，以便改寫後仍受檢查。
52. 身為研究者，我想 `aistat report <RUN>` 產出 `statistical_report.md`（APA 7 草稿），以便放進論文結果章節。
53. 身為研究者，我想用 `--lang en` 產出英文草稿，以便投國際期刊。
54. 身為研究者，我希望 Gate B 沒通過時不會產出宣稱已驗證的報告，以便不會誤用。
55. 身為統計初學者，我想用 `--mode learning` 得到 `learning_notes.md`，以我自己的變項回答「研究問題、為何選這方法、為何不選其他方法、假設怎麼理解、效果量與 CI 怎麼解讀、結果能支持什麼結論」，以便學會統計。

### 重現、匯出與紀錄

56. 身為研究者，我希望每次分析有獨立的 `runs/RUN_YYYYMMDD_NNN/` 資料夾，以便管理多次分析。
57. 身為研究者，我希望 run 的狀態依狀態機前進（PLAN_DRAFTED → JEV_GATE_A → USER_APPROVAL → EXECUTING → EXECUTED → JEV_GATE_B → REPORT_GENERATED → EXPORTED，及 BLOCKED / FAILED / CANCELLED），以便知道目前進度。
58. 身為研究者，我想 `aistat status <RUN>` 與 `aistat runs` 看到 run 狀態與歷程，以便掌握分析進度。
59. 身為研究者，我希望 `execution_log.json` 記錄每次狀態轉移、指令、引擎、耗時、警告與錯誤，但不記錄個別資料值，以便稽核又保護隱私。
60. 身為研究者，我希望 `manifest.json` 記錄資料雜湊、引擎與版本、方法、參數、檔案清單與雜湊，以便日後重現。
61. 身為研究者，我想 `aistat rerun <RUN>` 用同一份程式碼與資料重跑並比對輸出是否一致，以便驗證可重現性。
62. 身為研究者，我想 `aistat export <RUN>` 匯出 zip 成果包，預設不含原始資料（只含雜湊），以便分享給指導教授又不外流病人資料。
63. 身為研究者，我想用 `--include-data` 明確選擇把資料放進成果包，以便在獲授權時完整交付。
64. 身為研究者，我想 `aistat cancel <RUN>` 取消一個不再需要的 run，以便保持紀錄清楚。

### AI Agent 整合

65. 身為使用 Claude Code 的研究者，我想透過 MCP Server 讓 Agent 列出資料集、檢查資料、建立與驗證計畫、執行已核准分析、取得結果、審查與產生報告、匯出成果包，以便用自然語言完成分析。
66. 身為研究者，我希望 Agent 無法透過 MCP 自行核准計畫，以便「核准」永遠是人的決定。
67. 身為研究者，我希望 MCP 與 CLI 使用同一個 Core 服務，以便兩個入口的統計規則一致。
68. 身為研究者，我希望 repo 內附 Agent Skills（Data Inspector、Statistical Planner、Result Reviewer、Statistical Tutor 等），以便 Agent 知道每一步該做什麼、不能做什麼。
69. 身為研究者，我希望 Agent Skills 明確禁止 Agent 自行產生統計數值，以便所有數字都來自引擎。

## 實作決策（Implementation Decisions）

### 待決事項的預設決策

- **[預設] 名稱**：沿用暫定名 `aistat`，Python 套件名 `aistat`，正式名稱日後再定。
- **[預設] 授權**：Apache License 2.0（含專利授權條款，對醫療研究機構較友善）。R 以獨立子行程呼叫、不連結也不散布 R，因此不受 GPL 散布義務影響；PSPP（GPL）延後到後續版本並先評估。
- **[預設] CLI 框架與封裝**：Python ≥ 3.10、Typer、`pyproject.toml`（hatchling）、`src/` layout，安裝後提供 `aistat` 指令。
- **[預設] R 與 Python 分工**：Python 負責 CLI、Core、資料匯入、審查、報告、MCP；統計數值一律由「引擎」計算。R（僅需 base R，不需額外套件）與 Python（SciPy、statsmodels）都是引擎，各自產生並執行獨立腳本。`--engine auto` 時 R 優先，找不到 R 才用 Python。
- **[預設] 第一版方法**：descriptives、paired-t-test、independent-t-test、chi-square、correlation（pearson / spearman）、linear-regression。需求書 CLI 範例中的 `anova` 延後（不在 MVP 必須清單）。
- **[預設] AI 模式**：`aistat ai` 內建 LLM 對話延後；MVP 的 AI 工作流程以「Claude Code 等外部 Agent + MCP Server + Agent Skills」實現，CLI 本身完全不依賴 LLM。
- **[預設] 本機 / 雲端 LLM**：平台本身不呼叫任何 LLM，也不傳送資料到外部；Agent 端是否使用雲端模型由使用者環境決定，Skills 內要求 Agent 只傳摘要資訊、不貼個別病人資料。

### 模組

- **Workspace（Core 服務門面）**：CLI、MCP 共用的唯一入口。提供 init / open、import_dataset、list_datasets、inspect、set_variable_level、create_plan、approve、execute、review、report、export、rerun、cancel、get_run、list_runs。所有規則（狀態機、Gate、權限）在這一層，入口層只做參數轉換與顯示。
- **Data**：讀取 CSV / Excel，轉成 canonical CSV（UTF-8、空字串為缺失），計算原始檔與 canonical 檔 SHA-256，推論變項型態與測量尺度，產生資料字典與品質報告。原始檔與 canonical 檔設為唯讀。
- **Methods（方法規格）**：每個方法宣告變項角色（例如 paired-t-test 的 `before`、`after`）、每個角色接受的尺度、選項（alpha、alternative、correlation 的 `method`）、需要檢查的假設、最小樣本數。Gate A、CLI 驗證、報告模板都讀這份規格。
- **Validation（JEV）**：Gate A 與 Gate B，輸出 JEV check 清單；資料結構固定為 `{gate, check_id, verdict, evidence, reason, required_action}`，與需求書第 5 節一致。
- **Engines**：`EngineAdapter` 介面——`name`、`is_available()`、`version()`、`render_script(plan) -> str`、`execute(run_dir, timeout)`。R adapter 產生 `analysis.R` 以 `Rscript` 執行；Python adapter 產生 `analysis.py` 以目前 Python 直譯器執行。腳本讀 canonical CSV，寫 `raw_outputs/results.json`。新增引擎只需新增 adapter 並註冊，不改 CLI 與 Core 流程。
- **Reporting**：從 `results.json` 與計畫生成 APA 7 草稿（zh-TW / en）與 Learning notes。報告中的數字只由格式化函式從原始輸出產生。
- **Audit**：run 層級 `execution_log.json`、workspace 層級 `audit.jsonl`；只記錄中繼資料（指令、狀態、雜湊、耗時、錯誤），不記錄資料值。
- **MCP Server**：以 MCP Python SDK 包裝 Workspace，提供需求書第 4 節的 10 個工具；**不提供 approve 工具**。
- **Agent Skills**：`agents/skills/<skill>/SKILL.md`，對應需求書 Layer 3 的角色，說明觸發條件、輸入輸出（指向 `schemas/`）、可用工具、禁止事項、錯誤處理。

### Workspace 目錄契約

```text
<workspace>/
├── .aistat/
│   ├── workspace.json        # 版本、資料集登錄
│   └── audit.jsonl
├── data/<DATASET_ID>/
│   ├── original.<ext>        # 唯讀
│   ├── data.csv              # canonical，唯讀
│   └── dictionary.json
└── runs/RUN_YYYYMMDD_NNN/    # 需求書第 10 節結構
```

### 分析計畫契約（`analysis_plan.json`）

```json
{
  "run_id": "RUN_20261020_001",
  "dataset_id": "pretest_posttest",
  "dataset_sha256": "…",
  "method": "paired-t-test",
  "variables": {"before": "pre_score", "after": "post_score"},
  "options": {"alpha": 0.05, "alternative": "two-sided", "conf_level": 0.95},
  "missing_strategy": "complete-pairs",
  "group_levels": null,
  "assumptions": ["normality_of_differences"]
}
```

- 獨立樣本 t 檢定的 `group_levels` 由 Core 在建立計畫時決定（排序後的兩個值），引擎照用，確保 R 與 Python 方向一致（差值 = 第一組 − 第二組）。
- 卡方檢定使用 Pearson χ²（不做 Yates 連續性校正），與 SPSS「Pearson Chi-Square」列一致。
- Spearman 相關的 p 值使用 t 近似（R `exact = FALSE`），兩引擎一致。
- 線性迴歸 MVP 只接受 scale 預測變項與 0/1 二元數值變項；多類別 nominal 預測變項在 Gate A 判 NO（虛擬變項延後）。

### 狀態機

```text
PLAN_DRAFTED → JEV_GATE_A ─(有 NO)→ BLOCKED
JEV_GATE_A → USER_APPROVAL（所有 UNCERTAIN 經 --confirm）
USER_APPROVAL → EXECUTING → EXECUTED ｜ FAILED
EXECUTED → JEV_GATE_B ─(有 NO)→ 停在 EXECUTED（記錄 result_review.json）
JEV_GATE_B → REPORT_GENERATED → EXPORTED
任一非終止狀態 → CANCELLED
```

- run 建立時的歷程先寫入 CREATED、IMPORTED、PROFILED（記錄資料集雜湊與品質報告快照），再進 PLAN_DRAFTED。
- `report` 會先跑 Gate B；Gate B 有 NO 則拒絕輸出報告。UNCERTAIN 不擋報告，但列在報告末的「審查提醒」。
- `rerun` 不改變狀態，只把比對結果寫入 execution log；FAILED 的 run 可以修正環境後再 `analyze`。

### Gate A 檢查項目

| check_id | 判斷 |
|---|---|
| `variables_exist` | 角色指定的欄位都存在 → YES，否則 NO |
| `measurement_level` | 每個角色的尺度符合方法要求 → YES；不符 → NO；尺度為系統推論且屬可疑（例如數值但相異值 ≤ 7）→ UNCERTAIN |
| `group_structure` | 獨立 t 的分組恰兩組、卡方每變項 ≥ 2 類 → YES，否則 NO |
| `pairing_structure` | 配對 t：未確認前 UNCERTAIN（需確認前後測為相同受試者） |
| `independence` | 獨立 t、卡方：未確認前 UNCERTAIN（需確認觀察值互相獨立） |
| `missing_data` | 依缺失策略計算排除人數：排除比例 ≤ 5% → YES；> 5% → UNCERTAIN |
| `sample_size` | 有效樣本達方法最低需求 → YES，否則 NO |
| `assumptions_planned` | 列出引擎將檢查的假設 → YES |

### Gate B 檢查項目

| check_id | 判斷 |
|---|---|
| `engine_provenance` | `results.json` 存在、含引擎名稱版本、資料雜湊與計畫一致 → YES，否則 NO |
| `values_traceable` | 草稿中每個數字都能對應到原始輸出格式化值或計畫參數 → YES；有無法對應者 → NO |
| `p_value_format` | 無 `p = .000`、無 `p = 0.xxx` 前導零、極小值寫 `p < .001` → YES，否則 NO |
| `effect_size_ci` | 效果量與 CI 有限、CI 下限 < 上限 → YES；|d| > 3 或 CI 缺失 → UNCERTAIN |
| `causal_language` | 草稿含因果用語 → NO |
| `significance_consistency` | 「達顯著／未達顯著」與 p、α 一致 → YES，否則 NO |
| `assumptions_met` | 引擎假設檢查均未違反 → YES；有違反 → UNCERTAIN（附替代方法建議） |

### 安全

- 引擎指令白名單：只執行 `Rscript` 與目前的 Python 直譯器，不經 shell；預設逾時 120 秒，可用 `--timeout` 調整。
- 原始資料與 canonical 資料匯入後設為唯讀；Core 不提供修改資料的 API。
- 成果包預設不含資料；log 不含資料值。

## 測試決策（Testing Decisions）

- **好測試的定義**：只透過公開介面驗證外部可觀察行為；期望值來自獨立來源（R 官方範例輸出、手算教科書例題），不在測試裡用同樣算法重算。
- **測試 seam（依 `CLAUDE.md` 採推薦答案，不另停下確認）**：
  1. **Workspace 門面**（主要 seam）：init → import → inspect → plan → approve → execute → review → report → export → rerun 的行為、狀態機與 Gate 判斷。抓得到流程規則錯誤；抓不到 CLI 參數解析錯誤。
  2. **CLI**（Typer CliRunner）：少量端對端測試，確認指令、參數、輸出訊息與 exit code。抓得到入口層錯誤；不重複測 Gate 細節。
  3. **Engine golden cases**：同一份已知資料分別交給 R 與 Python 引擎，對照已知文獻值（容許誤差 1e-4）並交叉比對兩引擎（容許誤差 1e-6）。R 不存在時相關測試 skip。
  4. **MCP Server**：以 SDK 的 in-process 呼叫確認工具清單與一條核心流程，且無 approve 工具。
- **Prior art**：本 repo 尚無既有測試，以上即為第一批。
- 產出的 JSON 檔以 `schemas/` 下的 JSON Schema 驗證。
